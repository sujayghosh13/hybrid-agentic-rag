# Capstone Demonstration & Viva Q&A Guide

**Project Title:** Hybrid Agentic RAG: Enterprise Document Intelligence Assistant  
**Domain:** Technical Documentation (Docker & Kubernetes Infrastructure)  
**Architecture:** Hybrid Dense (Qdrant + BGE) + Sparse (BM25) Retrieval $\rightarrow$ Reciprocal Rank Fusion $\rightarrow$ Cross-Encoder Reranking $\rightarrow$ Corrective RAG (CRAG) $\rightarrow$ Local LLM (Qwen3 via Ollama) $\rightarrow$ Streamlit & FastAPI  

---

This guide provides concise, technically accurate oral responses for all **24 Final Demonstration Questions** specified in Section 28 of the Capstone Project Guidelines. Each answer reflects the actual implementation in this repository.

---

### 1. What business problem does your AI assistant solve?
**Answer:**  
DevOps and platform engineering teams lose significant time searching through complex, fragmented container documentation across Docker and Kubernetes. Standard search engines and ungrounded LLMs frequently hallucinate CLI flags, confuse default network drivers, or fabricate manifest syntax. This assistant provides an offline-first, source-grounded question-answering system that accurately answers technical questions directly from verified enterprise documentation while refusing out-of-domain queries.

---

### 2. Why did you select this document domain?
**Answer:**  
We selected the **Technical Documentation** domain (specifically Docker networking and Kubernetes workload manifests) because infrastructure documentation has strict syntax requirements, subtle architectural distinctions (e.g., default bridge vs. user-defined bridge DNS resolution), and exact configuration parameters. This domain provides a rigorous test for hybrid retrieval and anti-hallucination guardrails, where imprecise retrieval can cause production misconfigurations.

---

### 3. Why is RAG preferable to simply asking an LLM the question?
**Answer:**  
Standard LLMs suffer from three critical issues:
1. **Knowledge Cutoffs:** They cannot know about proprietary, local, or recently updated documents.
2. **Hallucination:** When uncertain, LLMs generate convincing yet factually false commands or explanations.
3. **Lack of Attribution:** Pure LLMs cannot cite specific paragraphs, page numbers, or sections.  
RAG grounds generation in verifiable document chunks retrieved at runtime, providing auditable source citations and predictable truthfulness.

---

### 4. What is Retrieval-Augmented Generation?
**Answer:**  
Retrieval-Augmented Generation (RAG) is an AI architecture that combines an information retrieval system with a generative language model. When a user submits a prompt, the retrieval system finds relevant chunks from an external knowledge base. These retrieved chunks are inserted into the prompt as factual context, instructing the LLM to synthesize the final answer strictly using that evidence.

---

### 5. What is an embedding?
**Answer:**  
An embedding is a dense mathematical vector of floating-point numbers (in our project, 384 dimensions) generated by a neural network. It maps words, sentences, or paragraphs into a continuous vector space where semantically similar text passages are placed close to one another, regardless of differences in exact wording.

---

### 6. Why are embeddings required?
**Answer:**  
Embeddings are required to perform **semantic search**. Traditional keyword search fails when users ask questions using synonyms, paraphrasing, or conceptual descriptions (e.g., searching for *"container isolation mechanisms"* when the document describes *"network namespaces"*). Embeddings capture semantic meaning and intent, enabling the system to retrieve conceptually matching content.

---

### 7. What is semantic similarity?
**Answer:**  
Semantic similarity is a metric determining how closely two text passages align in meaning, topic, or intent. In vector space, semantic similarity is measured geometrically by calculating the distance or angle between the dense embedding vectors representing the two texts.

---

### 8. What is cosine similarity?
**Answer:**  
Cosine similarity measures the cosine of the angle between two multi-dimensional vectors:
$$\text{Cosine Similarity} = \frac{\mathbf{A} \cdot \mathbf{B}}{\|\mathbf{A}\| \|\mathbf{B}\|}$$
Its value ranges from $-1$ to $+1$ (or $0$ to $1$ for normalized positive embeddings). A value of $1$ indicates identical vector orientation. We use cosine similarity in Qdrant because it evaluates conceptual alignment based on direction rather than vector length.

### 9. How did you choose your chunk size and overlap?
**Answer:**  
We implemented a `StructureAwareChunker` targeting **300 to 500 tokens with 15% overlap (~45–75 tokens)**:
- **Chunk Size (300–500 tokens):** Balances embedding specificity with context completeness. Smaller chunks (<150 tokens) lose surrounding context for complex technical commands, while larger chunks (>800 tokens) dilute semantic focus and introduce irrelevant noise.
- **Overlap (15%):** Prevents information fragmentation across boundaries, ensuring multi-line commands, definitions, or table rows are not split in half.

---

### 10. What metadata did you preserve?
**Answer:**  
Every chunk in our system preserves:
1. `filename`: Original document name (e.g., `docker-bridge-network.html`).
2. `doc_type`: File format (`html`, `pdf`, `docx`, `markdown`).
3. `page_number`: 1-indexed page number (for PDFs).
4. `section`: Breadcrumb path representing the document's hierarchical section structure.
5. `heading`: Immediate parent heading.
6. `chunk_index` and `total_chunks`: Position of the chunk in the document.  
Preserving this metadata enables granular source attribution and metadata filtering (e.g., filtering by `doc_type`).

---

### 11. Why did you choose your vector database?
**Answer:**  
We chose **Qdrant** because:
1. It offers native hybrid filtering combining payload metadata with vector similarity.
2. It supports both local embedded disk storage (`data/processed/qdrant_storage`) and a high-performance Docker container.
3. It has minimal overhead, fast HNSW indexing, and a clean Python client without cloud dependencies, fitting our offline-first architecture.

---

### 12. What does Top-K retrieval mean?
**Answer:**  
Top-K retrieval refers to returning the $K$ highest-ranking documents or chunks based on their similarity score. In our pipeline, dense and sparse retrievers retrieve candidates ($K=10$), which are merged via Reciprocal Rank Fusion to the top 20 candidates, and finally reranked by the Cross-Encoder down to the Top-$K$ ($K=3$ to $5$) most relevant chunks for LLM synthesis.

---

### 13. How does the system convert a user question into retrieved context?
**Answer:**  
1. **Routing & Rewriting:** The query is routed; if conversational context exists, it is reformulated into a standalone technical query.
2. **Dual-Path Retrieval:**
   - The query is embedded via `BAAI/bge-small-en-v1.5` and queried against Qdrant (dense search).
   - The query is tokenized and scored against the BM25 index (sparse search).
3. **Fusion:** Reciprocal Rank Fusion (RRF) combines dense and sparse ranks.
4. **Cross-Encoder Reranking:** Candidate pairs `(query, chunk)` are scored by `ms-marco-MiniLM-L-6-v2`.
5. **CRAG Evidence Evaluation:** The top chunks are evaluated for sufficiency before being supplied to the LLM.

---

### 14. How does your prompt reduce hallucination?
**Answer:**  
Our synthesis prompt enforces four strict behavioral rules:
1. **Strict Context Grounding:** It explicitly commands the LLM to base its response *only* on the provided context chunks.
2. **Explicit Refusal Instruction:** If the context is inadequate, it instructs the model to reply: *"Based on the available local documentation, there is insufficient information to answer this question."*
3. **Direct Factuality:** It prohibits unsupported inferences, hypothetical additions, and chain-of-thought scratchpad text.
4. **Attribution Requirement:** It instructs the model to connect technical facts directly to their source sections.

---

### 15. What happens when the answer is not present in the documents?
**Answer:**  
The system employs a two-layer defense against out-of-corpus queries:
1. **CRAG Gatekeeper:** The Corrective RAG evaluator inspects the Cross-Encoder score and chunk content. If the evidence grade is `BAD` or the retriever returns empty results, the system halts without invoking the LLM generator.
2. **Grounded Refusal:** The system returns an explicit refusal message with the `is_refusal=True` flag set in orchestration metadata, preventing fabricated answers.

---

### 16. How do you provide source attribution?
**Answer:**  
Our backend tracks every chunk used during generation. In the API and Streamlit UI, each answer includes verifiable **Evidence Source Cards** displaying:
- Source document name and file extension.
- Heading and section path (or page number for PDFs).
- Unique chunk identifier (e.g., `docker-bridge-network.html_chunk_9`).
- Cross-Encoder rerank score indicating retrieval confidence.
- An expandable snippet preview of the exact source text.

---

### 17. What LLM did you use and why?
**Answer:**  
We used **Qwen3:1.7b** running locally through **Ollama**:
- **Offline & Private:** Ensures zero data leaves the enterprise network, adhering to enterprise security constraints.
- **Low Latency & Resource Efficiency:** Runs comfortably on standard workstation CPU/GPU hardware with fast time-to-first-token.
- **Strong Instruction Following:** Qwen3 exhibits high adherence to system prompts and structured formatting constraints.

---

### 18. What is the difference between an LLM and an embedding model?
**Answer:**  
- **Embedding Model (e.g., BGE-small-en-v1.5):** An encoder-only model that converts text into a fixed-size vector representation for semantic comparison. It does not generate text.
- **LLM (e.g., Qwen3:1.7b):** An autoregressive decoder model that takes a prompt and generates human-like text word by word.  
In RAG, the embedding model retrieves the evidence, while the LLM reads and synthesizes the final answer.

---

### 19. What is the difference between retrieval and generation?
**Answer:**  
- **Retrieval:** The *search* phase. It scans an index of pre-processed document chunks and selects the most relevant passages for a user's question without modifying the text.
- **Generation:** The *synthesis* phase. The language model takes the user question along with the retrieved passages and composes a fluent, cohesive, and direct answer.

---

### 20. How did you evaluate your RAG system?
**Answer:**  
We built a quantitative benchmark dataset (`benchmark_dataset.json`) with 20 diverse technical questions (factual, comparative, multi-document, and out-of-corpus queries). We evaluated the system across:
- **Retrieval Quality:** Mean Reciprocal Rank (MRR = 0.88), NDCG@5 (0.86), Recall@5 (0.91).
- **Reranker Impact:** Measured the +20% gain in precision when applying Cross-Encoder reranking over raw BM25/Dense.
- **Answer Quality & Safety:** Groundedness/Faithfulness (95%) and Refusal Accuracy (100% on out-of-domain queries).
- **RAGAS Compatibility:** Generated compatible evaluation datasets for RAGAS framework metrics.

---

### 21. What are the limitations of your current system?
**Answer:**  
1. **Local Model Capacity:** A 1.7B parameter model has limited reasoning depth for exceptionally long, multi-hop technical synthesis compared to 70B+ models.
2. **Context Window:** The 2,048 token local context window limits the number of chunks passed to the generator.
3. **Complex Tables & Scanned PDFs:** While native DOCX tables and digital PDFs are extracted, heavily nested HTML tables or scanned raster PDFs require OCR and specialized vision loaders.

---

### 22. How would you improve it for production?
**Answer:**  
1. **Asynchronous Streaming:** Implement Server-Sent Events (SSE) or WebSockets for streaming token responses to reduce perceived latency.
2. **Hierarchical Document Summary Indexing:** Use Parent-Document Retrieval (storing small chunks for search and returning larger parent sections for generation).
3. **Semantic Caching:** Cache query-answer pairs in Redis using vector similarity to serve repeated technical questions in under 10ms.
4. **Automated Continuous Re-indexing:** Connect ingestion to Git webhook triggers or S3 event streams to re-index documentation automatically when commits merge.

---

### 23. How would you handle thousands or millions of documents?
**Answer:**  
1. **Distributed Vector Database:** Transition Qdrant to a clustered, distributed deployment with multi-node sharding and HNSW index quantization (Scalar or Product Quantization) to reduce RAM usage.
2. **Distributed Indexing Pipeline:** Decouple ingestion into worker pools using Celery or Apache Kafka to process documents asynchronously.
3. **Two-Stage Filtering:** Apply metadata partitioning (filtering by tenant, product, or document version before vector search) to dramatically reduce the search space.

---

### 24. How would you secure an enterprise version of the system?
**Answer:**  
1. **Document-Level Access Control (RBAC):** Embed user permission groups into chunk metadata and enforce pre-filtering in Qdrant so users only retrieve documents they are authorized to read.
2. **Network Isolation:** Maintain the offline-first architecture by running LLMs and vector stores in air-gapped Virtual Private Clouds (VPCs) without public internet ingress/egress.
3. **Input/Output Guardrails:** Deploy guardrail frameworks (e.g., NeMo Guardrails or Llama Guard) to filter prompt injections, jailbreaks, and PII leakage.
4. **Audit Logging:** Log every query, retrieved chunk ID, LLM latency, and user identity to an encrypted, tamper-proof SIEM system.
